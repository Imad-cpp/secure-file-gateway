# Engineering Decisions

This file records decisions that shape the V1 security boundary. It is intentionally lightweight; decisions with broader or irreversible consequences can later be promoted into individual ADR files.

## D-001 — API-first modular monolith

**Status:** Accepted for V1

**Decision:** Build one Laravel application with explicit internal modules/boundaries instead of multiple services.

**Why:** the portfolio goal is to demonstrate clear security and backend reasoning without distributed-system complexity. Transactions, lifecycle rules, deployment and local development remain understandable while internal modules still separate identity, ingestion, scanning, delivery and audit responsibilities.

**Rejected for V1:** microservices and a second application backend.

## D-002 — PostgreSQL is the metadata source of truth

**Status:** Accepted for V1

**Decision:** File ownership, lifecycle state, scan outcome references and audit records are persisted in PostgreSQL.

Object storage is the source of file bytes, not the authority for application lifecycle state.

## D-003 — Two private storage zones

**Status:** Accepted for V1

**Decision:** Separate untrusted quarantine content from clean releasable content using two private logical storage zones.

**Why:** a quarantined object must never become downloadable merely because it exists in object storage. Production-style permissions should be separable even if local development uses one MinIO instance.

## D-004 — Asynchronous scanning

**Status:** Accepted for V1

**Decision:** File upload returns before malware scanning finishes; scan work is processed through a queue.

**Consequence:** clients observe lifecycle state and receive `202 Accepted` for successful ingestion.

## D-005 — Fail closed

**Status:** Accepted for V1

**Decision:** scanner errors, timeouts or unavailable dependencies never produce `AVAILABLE`.

**Why:** uncertainty is not equivalent to a clean result.

## D-006 — Small format allowlist

**Status:** Accepted for V1

**Decision:** V1 accepts only PDF, PNG, JPEG and plain text, with a 10 MiB per-file limit.

Any expansion requires explicit security review and tests.

## D-007 — Server-side MIME detection

**Status:** Accepted for V1

**Decision:** the client-provided content type is not trusted. The server detects MIME and validates it against the permitted extension/MIME mapping.

## D-008 — Generated object names

**Status:** Accepted for V1

**Decision:** original filenames are display metadata only. Storage keys are generated by the server.

**Implementation:** quarantine keys use server-owned UUIDs and do not preserve a user-provided extension or filename.

## D-009 — Per-owner duplicate detection only

**Status:** Accepted for V1

**Decision:** SHA-256 detects duplicates within the same authenticated owner's files. V1 does not expose cross-user duplicate information or perform cross-user physical deduplication.

**Implementation:** owner + SHA-256 uniqueness is enforced in PostgreSQL in addition to the application pre-check, protecting the boundary from concurrent duplicate races.

## D-010 — Short-lived signed delivery

**Status:** Accepted for V1

**Decision:** clean objects remain private. The application issues short-lived signed access only after authentication, authorization and lifecycle checks.

**Known limitation:** a valid signed URL is a temporary bearer capability and can be shared until it expires.

## D-011 — Bearer-token authentication for V1

**Status:** Accepted for V1

**Decision:** use Laravel Sanctum personal-access/bearer tokens for the API-first demo.

A future frontend can use a different Sanctum mode without changing file ownership semantics.

## D-012 — Scanner behind an adapter

**Status:** Accepted for V1

**Decision:** domain/application code depends on a scanner interface rather than a scanner-specific API.

**Why:** malware-engine choice is infrastructure detail; tests need deterministic clean/unsafe/error outcomes without requiring a real engine in every unit test.

## D-013 — No archive extraction or remote ingestion in V1

**Status:** Accepted for V1

**Decision:** V1 does not unpack archives and does not fetch files from client-supplied URLs.

**Why:** these features introduce additional attack surfaces such as decompression abuse, nested content complexity and SSRF.

## D-014 — Audit events are safe metadata, not payload capture

**Status:** Accepted for V1

**Decision:** security events are append-oriented records of actor/action/target/outcome/correlation data. Tokens, signed URLs, file bodies and credentials are prohibited.

## D-015 — Documentation before implementation drift

**Status:** Accepted for V1

**Decision:** architecture, security model, API map and Definition of Done are reviewed before implementation. Material changes to the security boundary update these documents in the same change.

## D-016 — UUID identifiers for users and stored files

**Status:** Accepted for V1

**Decision:** user and stored-file primary/public identifiers use UUIDs rather than sequential integers.

**Boundary:** UUIDs are not authorization. Every resource operation still requires explicit ownership checks.

## D-017 — Foreign-owned file identifiers fail as not found

**Status:** Accepted for V1

**Decision:** when an authenticated user supplies another user's file identifier, owner-policy denial is rendered as `404` rather than a distinct `403` ownership signal.

**Why:** this reduces resource-enumeration leakage while preserving normal owner access semantics.

## D-018 — Authentication throttle is explicit and testable

**Status:** Accepted for V1

**Decision:** registration/login surfaces use a default limit of 5 attempts per minute keyed by normalized email + client IP.

**Configuration:** `AUTH_RATE_LIMIT_PER_MINUTE=5`.

## D-019 — API bearer tokens expire by default

**Status:** Accepted for V1

**Decision:** newly issued Sanctum bearer tokens have a default 720-minute (12-hour) lifetime, and logout revokes only the current token.

**Configuration:** `API_TOKEN_TTL_MINUTES=720`.

## D-020 — Upload creation has an independent throttle

**Status:** Accepted for V1

**Decision:** authenticated upload creation uses a default limit of 10 requests per minute keyed by owner ID + client IP.

**Configuration:** `UPLOAD_RATE_LIMIT_PER_MINUTE=10`.

## D-021 — Quarantine precedes content-derived acceptance

**Status:** Accepted for V1

**Decision:** after authentication, request presence, size and extension checks, bytes are written to private quarantine before server-side MIME verification, hashing and duplicate persistence decisions.

**Failure behavior:** normal MIME mismatch, duplicate and metadata-persistence failure paths remove the newly written quarantine object. Reconciliation for cleanup failures remains hardening work.

## D-022 — ClamAV is the V1 scanner adapter

**Status:** Accepted for V1

**Decision:** use ClamAV `clamd` behind the `MalwareScanner` interface. Local Compose follows the `clamav/clamav:1.5` feature line so patch updates can be consumed without silently jumping feature lines.

**Boundary:** application/domain code continues to depend on the adapter interface, not ClamAV-specific result types.

## D-023 — Scanner communication is internal-only `INSTREAM`

**Status:** Accepted for V1

**Decision:** the worker streams quarantine bytes to `clamd` using the ClamAV `INSTREAM` protocol. It does not send user-controlled paths for the daemon to open.

**Network rule:** the local Compose configuration does not publish TCP/3310 to the host. `clamd` is reachable only inside the Compose network.

**Why:** the `clamd` TCP protocol itself is not an authenticated public API and must not be treated as an Internet-facing boundary.

## D-024 — Scan retries and timeouts are bounded

**Status:** Accepted for V1

**Decision:** a scan job receives 3 attempts, backoff of 5 then 30 seconds, a 30-second job timeout and per-file overlap protection. Redis `retry_after` remains 90 seconds.

**Why:** retry transient failures without allowing an uncertain result to become clean, while keeping job timeout below the queue retry horizon.

## D-025 — Clean storage promotion precedes `AVAILABLE`

**Status:** Accepted for V1

**Decision:** after a clean verdict, bytes are written to private clean storage before the metadata transition to `AVAILABLE`.

If the lifecycle update fails after the clean object is created, the normal compensation path removes the newly created clean object and the job fails closed.

**Why:** `AVAILABLE` must never point at an object that has not completed clean-storage promotion.

## D-026 — Unsafe and final-failure retention semantics differ

**Status:** Accepted for V1

**Decision:** an unsafe verdict transitions to `REJECTED` and never creates a clean object. The normal path deletes the quarantined unsafe object and clears its quarantine key after successful deletion. A final scanner/job failure transitions to `SCAN_FAILED` and keeps the quarantine object private for operational reconciliation.

**Why:** a known unsafe verdict and an uncertain infrastructure failure are different operational states. Neither is downloadable.

## D-027 — Scanner metadata is internal

**Status:** Accepted for V1

**Decision:** `scan_engine`, `scan_signature` and scan completion metadata may be stored for operations/tests but normal file APIs expose only user-safe lifecycle state.

**Why:** raw/internal scanner details are not required for normal-user decisions and should not become an accidental disclosure surface.

## D-028 — Queue handoff uses compensating cleanup

**Status:** Accepted for V1

**Decision:** metadata is persisted before scan dispatch so a queued worker can resolve the file immediately. If dispatch then fails, the application attempts to delete the new metadata row and quarantine object before returning `DEPENDENCY_UNAVAILABLE`.

If metadata compensation itself cannot complete, the quarantine object is deliberately preserved and the file is best-effort moved to `SCAN_FAILED` rather than deleting bytes that an existing database row may still reference.

**Known boundary:** V1 uses explicit compensation rather than a transactional outbox. Orphan/outbox reconciliation remains a possible hardening improvement if deployment requirements justify it.

## Deferred decisions

The following are intentionally not frozen yet:

- download/general API rate-limit numbers beyond the implemented authentication and upload throttles;
- signed URL lifetime;
- retention/cleanup durations;
- production hosting provider;
- project license;
- admin/auditor role in the public demo;
- whether a transactional outbox is required beyond V1 compensation semantics.

These will be decided when implementation evidence or a concrete requirement exists, rather than guessed in advance.
