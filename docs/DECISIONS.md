# Engineering Decisions

This file records decisions that shape the V1 security boundary. It is intentionally lightweight for the project foundation; decisions with broader or irreversible consequences can later be promoted into individual ADR files.

## D-001 — API-first modular monolith

**Status:** Accepted for V1

**Decision:** Build one Laravel application with explicit internal modules/boundaries instead of multiple services.

**Why:**

- the portfolio goal is to demonstrate clear security and backend reasoning, not distributed-system complexity;
- transactions and lifecycle rules are easier to reason about inside one application boundary;
- deployment and local development remain understandable;
- modules can still separate identity, ingestion, scanning, delivery and audit responsibilities.

**Rejected for V1:** microservices and a second application backend.

## D-002 — PostgreSQL is the metadata source of truth

**Status:** Accepted for V1

**Decision:** File ownership, lifecycle state, scan outcome references and audit records are persisted in PostgreSQL.

**Why:** lifecycle correctness and authorization need durable, queryable state with transactional support.

Object storage is the source of file bytes, not the authority for application lifecycle state.

## D-003 — Two private storage zones

**Status:** Accepted for V1

**Decision:** Separate untrusted quarantine content from clean releasable content using two private logical storage zones.

**Why:** a quarantined object must never become downloadable merely because it exists in object storage.

Production-style permissions should be separable even if local development uses one MinIO instance.

## D-004 — Asynchronous scanning

**Status:** Accepted for V1

**Decision:** File upload returns before malware scanning finishes; scan work is processed through a queue.

**Why:** scanning is external/resource-intensive work and should not hold the upload request open indefinitely.

**Consequence:** clients observe lifecycle state and receive `202 Accepted` for a successful ingestion request.

## D-005 — Fail closed

**Status:** Accepted for V1

**Decision:** scanner errors, timeouts or unavailable dependencies never produce `AVAILABLE`.

**Why:** uncertainty is not equivalent to a clean result.

## D-006 — Small format allowlist

**Status:** Accepted for V1

**Decision:** V1 accepts only PDF, PNG, JPEG and plain text, with a 10 MiB per-file limit.

**Why:** broad file-format support would increase parser/content attack surface before the core gateway is proven.

Any expansion requires explicit security review and tests.

## D-007 — Server-side MIME detection

**Status:** Accepted for V1

**Decision:** the client-provided content type is not trusted. The server detects MIME and validates it against the permitted extension/MIME mapping.

**Why:** filenames and browser-declared MIME values are attacker-controlled metadata.

## D-008 — Generated object names

**Status:** Accepted for V1

**Decision:** original filenames are display metadata only. Storage keys are generated by the server.

**Why:** prevents path/object-key manipulation and avoids making storage topology depend on user input.

## D-009 — Per-owner duplicate detection only

**Status:** Accepted for V1

**Decision:** SHA-256 is used to detect a duplicate within the same authenticated owner's files. V1 does not expose cross-user duplicate information or perform cross-user physical deduplication.

**Why:** global deduplication can become a presence oracle and is unnecessary for the portfolio objective.

## D-010 — Short-lived signed delivery

**Status:** Accepted for V1

**Decision:** clean objects remain private. The application issues short-lived signed access only after authentication, authorization and lifecycle checks.

**Why:** avoids permanent public URLs and keeps access tied to an application decision.

**Known limitation:** a valid signed URL is a temporary bearer capability and can be shared until it expires.

## D-011 — Bearer-token authentication for V1

**Status:** Accepted for V1

**Decision:** use Laravel Sanctum personal-access/bearer tokens for the API-first demo.

**Why:** it keeps API authentication explicit and avoids making cookie/session browser behavior part of the initial security boundary.

A future frontend can use a different Sanctum mode without changing file ownership semantics.

## D-012 — Scanner behind an adapter

**Status:** Accepted for V1

**Decision:** domain/application code depends on a scanner interface rather than a scanner-specific API.

**Why:** malware-engine choice is infrastructure detail; tests need deterministic clean/unsafe/error outcomes without requiring a real engine in every unit test.

The real scanner technology will be selected during implementation and documented separately.

## D-013 — No archive extraction or remote ingestion in V1

**Status:** Accepted for V1

**Decision:** V1 does not unpack archives and does not fetch files from client-supplied URLs.

**Why:** these features introduce additional attack surfaces such as decompression abuse, nested content complexity and SSRF.

## D-014 — Audit events are safe metadata, not payload capture

**Status:** Accepted for V1

**Decision:** security events are append-oriented records of actor/action/target/outcome/correlation data. Tokens, signed URLs, file bodies and credentials are prohibited.

**Why:** auditability must not create a second sensitive-data leak surface.

## D-015 — Documentation before implementation drift

**Status:** Accepted for V1

**Decision:** architecture, security model, API map and Definition of Done are reviewed before the first application scaffold. Material changes to the security boundary update these documents in the same change.

**Why:** the repository is intended to demonstrate traceable engineering decisions, not only final code.

## Deferred decisions

The following are intentionally not frozen yet:

- exact malware-scanner engine;
- exact queue retry/backoff numbers;
- exact API rate-limit numbers;
- signed URL lifetime;
- retention/cleanup durations;
- production hosting provider;
- project license;
- admin/auditor role in the public demo.

These will be decided when implementation evidence or a concrete requirement exists, rather than guessed in advance.
