# Definition of Done

A feature or release is not complete because the happy path works. This project is specifically intended to demonstrate backend and security engineering, so correctness includes negative paths, operational behavior and evidence.

## V1 release outcome

A user can authenticate, upload an allowed file, observe its processing state, and obtain controlled temporary access only after the file has passed validation and scanning.

A malicious, mismatched, oversized, unauthorized or scanner-failed file never becomes downloadable.

A signed content capability may be used without the original bearer token after owner-authorized issuance, but only while its signature is valid, unexpired and the resource remains `AVAILABLE`.

Operational/security evidence must also remain safe: request correlation is server-generated, audit metadata excludes prohibited sensitive fields, readiness fails closed without exposing dependency details, and deletion cleanup can be retried without broad bucket-wide deletion authority.

## Functional completion

V1 must include:

- local user registration/login suitable for the demo;
- bearer-token authentication;
- authenticated multipart upload;
- allowed extension policy;
- server-side MIME detection;
- 10 MiB maximum object size;
- generated storage names;
- SHA-256 calculation;
- per-owner duplicate detection;
- quarantine storage;
- queued malware-scan processing;
- explicit lifecycle state machine;
- clean private storage;
- owned-file listing and metadata read;
- controlled short-lived download access;
- deletion/cleanup behavior;
- audit events for security-relevant actions;
- server-generated request correlation;
- liveness/readiness health endpoints;
- targeted retry of known partial deletion cleanup.

The core application behavior above is now implemented. This does **not** make V1 complete while OpenAPI/release evidence, reproducible real-infrastructure integration evidence and remaining CI/release hardening requirements are unfinished.

## Authorization completion

Automated tests must prove:

- unauthenticated users cannot upload/list/read/delete or issue download capabilities;
- user A cannot read user B's metadata;
- user A cannot delete user B's file;
- user A cannot obtain download access for user B's file;
- object identifiers do not bypass ownership policy;
- lifecycle state is not arbitrarily client-writable;
- download capability issuance is denied for every state except `AVAILABLE`;
- signed content requires a valid, unexpired capability and current `AVAILABLE` state.

## File-security completion

Automated tests must prove:

- unsupported extension is rejected;
- declared/browser MIME is not trusted as the final type decision;
- extension/detected-MIME mismatch is rejected;
- oversized file is rejected;
- original filename cannot influence object-storage path;
- unsafe scanner result produces a non-downloadable rejected state;
- scanner failure does not fail open;
- duplicate scan-job execution remains safe;
- per-owner duplicate detection does not reveal another user's file existence;
- signed-capability tampering and expiry are rejected;
- deletion revokes previously issued capabilities;
- deletion does not falsely restore downloadability when storage cleanup is partial.

## Data and storage completion

- PostgreSQL migrations are deterministic and reversible where practical.
- Foreign keys/indexes support ownership, lifecycle and audit queries.
- quarantine and clean storage are private.
- quarantine objects are never used for normal delivery.
- object keys are generated by the server.
- database/storage partial failures have explicit behavior and tests for critical paths.
- rejected/deleted-object cleanup behavior is documented.
- deleted tombstones preserve lifecycle evidence without permanently blocking same-owner re-upload of identical bytes.
- retry reconciliation touches only object keys still referenced by `DELETED` rows.

## API completion

- `openapi.yaml` covers every public V1 endpoint and the temporary signed-content capability route.
- stable error envelope and codes are documented.
- `X-Request-ID` response semantics are documented.
- examples do not contain real credentials or personal data.
- API documentation matches implementation.
- pagination/filter behavior is tested where implemented.
- endpoint responses do not leak internal object keys, stack traces, raw scanner output or deleted historical digests.
- signed capability semantics, expiry and bearer-capability limitation are documented explicitly.
- health responses remain aggregate-only and do not reveal dependency-specific failures.

**Current API-contract status:** `openapi.yaml` now covers the public V1 + signed capability + health surface, is parsed by the PHP OpenAPI validator, and has an automated route/method drift check against Laravel.

## Security completion

Before V1 release:

- threat model in `docs/SECURITY_MODEL.md` reflects the implementation;
- `SECURITY.md` defines a private vulnerability-reporting route and supported-version policy;
- no secrets are committed in history created by this project workflow;
- CI uses minimum required permissions;
- third-party GitHub Actions are pinned to immutable commit SHAs where practical;
- dependencies receive an automated vulnerability/dependency review mechanism where GitHub supports it;
- application secrets come from environment/secret injection;
- logs exclude Authorization headers, bearer tokens, signed URLs, credentials and file bodies;
- audit metadata sanitizer excludes prohibited sensitive key classes;
- request-correlation IDs are server-generated and attached to normal/error responses;
- CORS is deny-by-default for unneeded origins;
- rate limits exist for auth, upload, download-capability and signed-content surfaces;
- readiness checks required dependencies and fails closed;
- debug mode is not enabled in production-style configuration.

The current hardening layer satisfies the request-correlation, audit-sanitization, concrete-readiness, targeted-deletion-reconciliation and `SECURITY.md` portions. A transactional forensic audit ledger, production observability stack and generic bucket-wide orphan sweeper are intentionally not claimed.

## Audit completion

V1 internal audit evidence must prove:

- registration success can be recorded;
- login success/failure can be recorded without submitted credentials in audit metadata;
- logout success can be recorded;
- accepted upload can be correlated to the target file without file-body/object-key capture;
- download-capability issued/denied outcomes can be recorded without the signed URL;
- deletion success/partial failure can be recorded without private storage keys;
- high-risk metadata key classes are recursively removed;
- audit string metadata is bounded;
- request IDs stored in HTTP-originated events match the server-generated response correlation ID.

**Current boundary:** audit persistence is best-effort and not transactionally coupled to every domain/storage side effect. V1 must document that limitation rather than imply forensic completeness.

## Readiness and reconciliation completion

Automated tests must prove:

- liveness does not depend on downstream readiness;
- readiness returns `200` only when its checker reports all required dependencies ready;
- readiness returns `503` fail-closed otherwise;
- the public readiness body does not disclose dependency-specific failures;
- caller-supplied request IDs do not replace server-generated correlation;
- error responses retain correlation IDs;
- deleted-object reconciliation cleans referenced residual objects and clears successful keys;
- reconciliation never touches non-`DELETED` rows;
- invalid reconciliation limits are rejected.

### Integration

At least one CI/local integration path must exercise the real database, Redis queue coordination and S3-compatible storage boundary.

**Current integration status:** CI boots PostgreSQL, Redis, MinIO, ClamAV and the non-root Laravel application, applies the real PostgreSQL migrations and requires `/health/ready` to verify every dependency. This satisfies the real dependency/readiness boundary.

The malware lifecycle suite may use deterministic test adapters in ordinary tests, but a full real-engine file-processing check is still required before the project claims end-to-end operational malware-scanning evidence.

## CI completion

Pull-request CI must fail on relevant quality problems and include, as the implementation matures:

- dependency installation with lockfile;
- formatting/style check;
- static analysis;
- automated tests;
- migration/database test path;
- API/spec validation;
- security/dependency checks appropriate to the ecosystem;
- secret hygiene checks.

CI configuration itself is reviewable code and follows least privilege.

The current `Application Quality` gate strictly validates and installs the committed Composer lock, runs Pint, Larastan/PHPStan level 5 without a baseline, the complete PHPUnit suite including OpenAPI route-drift checks, Composer audit, a separate full-history Gitleaks scan, and a real-container infrastructure/readiness job. The remaining release evidence is the full real-engine file-processing scenario plus final demo/release artifacts—not the core quality gates listed above.

## Local developer experience

A new contributor should be able to follow the README to:

1. clone the repository;
2. create a local environment from example configuration;
3. start PostgreSQL, Redis and S3-compatible storage;
4. install dependencies;
5. migrate the database;
6. run the application/worker;
7. run automated tests;
8. perform a sample upload, scan and controlled-download flow;
9. inspect readiness behavior;
10. retry known deleted-object cleanup using the documented reconciliation command.

No undocumented machine-specific setup should be required for the core demo.

## Portfolio evidence completion

Before this repository is linked as strong evidence from the personal GitHub profile, it should have:

- an understandable README with an architecture diagram;
- non-trivial implementation commits and PR history;
- green CI on `main`;
- automated security/authorization tests;
- sanitized sample API usage;
- clear project status;
- a tagged V1 release;
- no fake production claims;
- no real user data, private infrastructure identifiers or secrets.

## Not required for V1

The following do not block V1:

- frontend dashboard;
- public sharing;
- mobile application;
- microservices;
- Kubernetes;
- multi-region deployment;
- archive extraction;
- document previews;
- remote URL ingestion;
- AI features;
- generic bucket-wide orphan deletion;
- immutable external forensic audit storage.

Adding complexity that does not strengthen the gateway's core security evidence is not a completion requirement.
